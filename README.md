The mqtt2sqlite_msg program reads meshtastic messages arriving on an MQTT server, <strong>in json format and with a specific topic</strong>, and stores them in a sqlite3 database. 
The MQTT server must be running (see various guides online for installing it on your distro), and the meshtastic LORA cards must be configured to send data to the MQTT server on port 1883. Make sure the MQTT server allows access to this port and create a login user and password to enter in the LORA cards' configuration.<br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/mqtt_meshtastic_configuration.jpg)<br>
The mqtt2sqlite_msg program acts as a client and intercepts messages in transit. <strong>It must always be active in the background.</strong><br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/mqtt_sample_frames_in_json.jpg)<br><br>
<strong>The db2html_msg program can be run as a cron job</strong>. Its function is to extract a certain number of messages from the database and display them in a specially created HTML page.
In the configuration code, you must specify the database path and where the page should be created (usually a path within the existing web server).
You can also specify which channels to display, thus offering the possibility of having different pages for each meshtastic channel (the messages in the database are from all the channels configured on the lora cards). The code and HTML page are very simple, making it easy to customize.
These Python programs require libraries that must be installed manually.<br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/html_messages_dashboard.jpg)<br>
<br><br>
mqtt2sqlite_map connects to the MQTT server and acquires information about the nodes in transit, including their location and telemetry. A specific database is created for this information. <strong>This program must also always run in the background</strong>. Configuration requires the code to include the MQTT server login parameters, the maximum number of nodes to manage, and the time taken to determine whether a node is still operational.<br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/map.jpg)<br>
<strong>The db2map program must be run via cron (or manually)</strong>. Its function is to read the database populated by the previous program and display on a map the nodes that have passed (as information) through the MQTT server. Its configuration, always within the code, includes the path and name of the HTML page that will contain the map (an operational web server is required), the coordinates needed to set the center of our map, the zoom, and the radius (in km) that will encompass the nodes to be displayed. An additional parameter sets the presence (last information received) of the nodes on the map. The display (green marker) will contain the last telemetry received and recorded in the database or (blue marker) only the node's position, in the absence of other values. These codes, which are free to use and without any warranty, require specific Python libraries. Good knowledge of Python management is required, as well as operating on a complete web server.
<br><br>
The meshapp folder contains the programs to manage an application (a web app) capable of receiving and sending messages on the meshtastic network without the need to physically reach (or via the network) a Lora card, but <strong>by interfacing only with the MQTT server where the Lora cards are connected</strong>. These are tests and configurations that I have developed over time, very experimental, which may undergo operational changes depending on how the meshtastic firmware evolves. The first software to manage is the daemon that queries the database (created by the mqtt2sqlite_msg application) and makes the incoming messages available on websocket. So yes, in addition to the MQTT server which is operational, <strong>mqtt2sqlite_msg.py also needs to be in the background</strong> (it fetches messages from the Lora cards) and inserts them into the database, and finally the <strong>db_websocket_daemon.py which is always active</strong>.<br><br>
The daemon requires simple configuration within the code: the path to the database, the number of seconds to query the database (default 10), and the channel to be monitored (0 = primary channel). You can also specify the web socket port and how many messages to make available to anyone connecting to the web app (default: the last 10).<br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/meshapp/log_demone.jpg)<br>
Could everything have been managed with a single program? Yes, but the system has grown over time, maybe some people are only interested in publishing messages on a dashboard, so for now it's like this.<br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/meshapp/meshtastic_webapp.jpg)<br><br>
The meshapp.php software is a web app; it requires a web server like Apache or similar, and a PHP interpreter. It connects to the websocket port 8765/TCP (or the one configured in the daemon that reads messages from the database). You can use the Linux netstat command to verify that the daemon is active and listening. The web app is configured directly within the code; that is, you need to verify the path where we will place the program that transmits our messages. By default, the path is /opt/meshtastic and the application is message2mqtt.py. Verify that execution permissions are granted to this code. Check the daemon log to verify that the web app is connecting to the web socket. If the procedure is configured correctly, messages arriving at the MQTT server will be retrieved by the daemon and published via websocket, and our web app will display them in the table.<br><br>
The last program to be managed is <strong>message2mqtt.py</strong>. This software is the result of my analysis and comparisons. It certainly can be improved and needs some corrections, but I wanted to formalize the result I achieved. Basically, working with Protobuf, this code prepares a message (and a node info packet) to be sent over the meshtastic Lora network via the MQTT server where the cards are connected. Many applications can be developed with this system, from alarm alerts to bulletins. I had found various documentation online but never found any success with the application, then I finally managed to structure the various processes. The code can certainly be improved and will need to be adapted if the meshtastic protocol is modified in the future. I recommend avoiding spam by sending uncontrolled messages. The code has a configuration section where you can enter the connection parameters to the MQTT server. The next step is to configure a "virtual node" by specifying a series of information, particularly the name of the channel where the message will be sent. The topic is then prepared to communicate with the meshtastic cards, where /e is used for protobuf and /json for reading text from applications connected to MQTT. The code actually prepares (and sends) both frames.<br><br>
![](https://github.com/ik5xmk/mt_mqtt_jobs/blob/main/meshapp/output_msg2mqtt.jpg)<br><br>
This program is called from the web app with two distinct arguments: "-i" sends the node info frame to MQTT. "message text" sends the content. The syntax is clearly visible within the PHP code.<br><br>
